# Hybrid Literature

Act as the lead researcher. The Codex literature council searches read-only, a single Codex writer updates the knowledge base, and you own project relevance, candidate adjudication, verification, stopping, and the final answer. Stay in the main conversation and never run two `/lit` sessions against the same repository at once. The knowledge base is project-local, comprehensive per question, cumulative across the project's questions, and not portable.

Runs are multi-hour and heavy by design: each round uses ten Luna subagents at maximum effort, there may be five rounds, and the writer also uses Luna at maximum effort. Slow is not failed. The ingest-only branch keeps a small addition from triggering the full loop.

Only the writer changes the knowledge base. Do not edit knowledge-base files yourself. Research councils remain strictly read-only, and all knowledge-base writes go through the ingest script.

## Research and ingest

1. **Normalize the request.** Choose one of two branches. A research question enters the comprehensive round loop. User-supplied files or paths enter the ingest-only branch, including a request to add one paper; skip the search loop entirely. Read the project README and relevant documentation so relevance is judged against the project, not topical similarity alone.
2. **Locate or create the knowledge base.** Use `<project>/literature/`. When it is absent, run `${CLAUDE_SKILL_DIR}/scripts/run-codex-ingest.sh --init <project>`; this deterministically copies the skill's template, and no model authors the skeleton. On first use, instruct the writer to fill in the project research scope in `scope.md`. On later invocations, instruct it to append every question asked with its date and run link.
3. **Build and run each search round.** For the question branch, write a fresh packet to a uniquely suffixed temp file. Include the question and project context; the current `index.md`, `missing.md`, and `scope.md`; topic page titles; an explicit list of DOI, arXiv, and normalized-title identifiers already in the knowledge base; the slugs and identifiers of papers newly ingested in the previous round as explicit citation-chaining seeds; the round number; gaps from the previous round; and all previously rejected candidates with the lead's reasons. Keep that candidates ledger in a temp directory with stable IDs and carry it into every later packet. Include the report contract required by `$literature-council`. Run `${CLAUDE_SKILL_DIR}/scripts/run-codex-council.sh --skill literature-council <packet> <project>` as a background Bash command and wait without a timeout. Read `RESULT_FILE`. A `SUBAGENTS` value of `10` is full; below ten is partial and must be disclosed; `unknown` is unconfirmed and must not be described as full or partial. Count failed and partial rounds toward the five-round cap.
4. **Adjudicate every candidate.** Record an accept or reject decision and a reason under its stable ledger ID. Apply topical and project relevance, not a quota: treatment of the question must always be comprehensive. Send every accepted candidate to the writer.
5. **Ingest accepted candidates.** Write a fresh ingest packet and run `${CLAUDE_SKILL_DIR}/scripts/run-codex-ingest.sh <ingest-packet> <project>` for round one. In later rounds, use `${CLAUDE_SKILL_DIR}/scripts/run-codex-ingest.sh resume <SESSION_ID> <ingest-packet> <project>` when the session ID is known. Correctness must never depend on resume; a fresh writer is safe because the knowledge base is self-describing. Point to `<kb>/README.md` as the binding ingest specification instead of copying it. List each candidate's identifiers, best verified open URL, accepted relevance line, and the research question. Restate the hard rules: download only openly accessible copies; never bypass paywalls or logins; record every unretrievable paper in `missing.md` with complete metadata and a landing link; write knowledge-base files only inside `literature/`. Instruct the writer to maintain `topics/`, `runs/`, and `scope.md` as the packet requires.
6. **Verify every round.** Run `${CLAUDE_SKILL_DIR}/scripts/kb-check.py <kb>`. Read the new `paper.md` notes and the index diff, not all full texts. Spot-check two or three cited numbers against `fulltext.md`. Confirm the runner reported no policy violation and, in a git project, no tracked or non-ignored file outside `literature/` changed. Reconcile every nonzero removal count and every accepted candidate to either a paper package or a `missing.md` entry. Writer sentinels are self-reports; filesystem-verified counts and your inspection are the evidence.
7. **Apply the stop rule.** Run at least two rounds for every new question; round two must chain citations from round one's ingested papers. After round two, stop only when one full, valid round added nothing material and named no remaining gap. Continue after a zero-yield round that still names gaps. Stop after round five even if the gate is not met, and report `capped`. Describe any stop as operational saturation under the recorded scope and cutoff, never proof that no relevant literature exists.
8. **Answer and report.** Answer from the knowledge base with `[[slug]] p.N` citations. State what papers were added and which topics changed, the knowledge-base path, rounds run and the stopping reason, the `kb-check` result, and honest caveats such as extraction failures, abstract-only entries, or partial councils. Give a numbered list of missing papers with citation, DOI, and best landing link. Tell the user to put files in `literature/inbox/` or name any path and then tell the agent.
9. **Ingest follow-up files.** In the files branch, match files to `missing.md` by embedded DOI first. Use title and year only to flag ambiguity; never merge silently. Send an ingest-only packet, resuming the known writer session or starting fresh. Instruct the writer to copy matched files as `access: user-supplied`, mark them non-redistributable, extract them, write notes, move their entries from `missing.md` to `index.md`, and append to the run record. Ingest an unmatched file as a new paper. Then run `kb-check.py` and perform the same lead verification as a research round.

The ingest runner prints `STATUS=ok|no-change|degraded|unverified|failed`, `POLICY_VIOLATION`, filesystem counts in `PAPERS_ADDED`, `PAPERS_REMOVED`, `KB_FILES_CHANGED`, and `KB_FILES_REMOVED`, plus `RESULT_FILE` and `SESSION_ID`. `ok` means the report and verified KB delta agree, `no-change` means both report no KB change, `degraded` means the writer was partial or blocked or a policy violation was confirmed, `unverified` means the report and delta cannot be reconciled, and `failed` means there is no usable report. Any nonzero removal count makes the best possible status `unverified`; a confirmed policy violation or partial or blocked report still makes it `degraded`. `POLICY_VIOLATION=unknown` means policy compliance was not independently checkable here, which is normal outside git. Failed, degraded, and unverified ingest rounds still count toward the five-round cap. After every ingest round, reconcile every accepted candidate to either a paper package or `missing.md`. If resume fails, start a fresh writer session. Do not edit the project or commit while the writer runs; concurrent edits are indistinguishable from outside-KB writes.
