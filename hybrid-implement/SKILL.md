# Hybrid Implement

Act as the lead. A single Codex session implements; review advisers stay strictly read-only; you own the specification, every accept-or-reject decision, and termination. Stay in the main conversation — do not run this skill inside a subagent.

Only the Codex implementer writes to the project, and only through the implement script. Do not edit project files yourself during the run, never run two implement sessions at once, and never push. Write access is not sandboxed: instructions forbid out-of-scope changes, and the script's preconditions and post-run git checks detect repository drift rather than prevent it, so honor its status contract exactly.

## Implement, review, fix

1. Normalize the request — a prompt, an earlier conversation or council result, or a plan file — into one implementation packet: objective, acceptance criteria, constraints, non-goals, pointers to relevant files, and the checks Codex should run. Before freezing the packet, check the requested approach against the code it will change; if a materially simpler or safer approach meets the objective, raise it with the user before implementing, not after. Choose the level of detail the task needs; the packet is the specification of record and stays frozen for the run.
2. Preflight: the project must be a git repository; work on whatever branch is checked out — where the work lands is the user's call, not the skill's. Record the baseline commit. The script refuses a dirty tree so Codex's changes stay attributable and reviewable; when the user wants Codex to build on uncommitted work, rerun it with `HYBRID_IMPLEMENT_ALLOW_DIRTY=1`. Neither you nor Codex commits anything — commit only when the user asks directly or through a user-invoked enclosing skill whose contract commits each gated increment.
3. Run `${CLAUDE_SKILL_DIR}/scripts/run-codex-implement.sh <packet-file> /path/to/project` as a background Bash command and wait — implementation can far exceed the ten-minute foreground cap, and slow is not failed. The script prints `STATUS` (`ok`, `no-change`, `degraded`, `unverified`, `failed`) alongside git-verified facts: `POLICY_VIOLATION` names forbidden drift such as a moved HEAD or switched branch, `CHANGED_FILES` counts files changed against the baseline commit (tracked plus untracked), `PATCH_FILE` holds the tracked diff, and `RESULT_FILE` holds Codex's report with its self-reported `IMPLEMENT_STATUS` and `IMPLEMENT_TESTS` sentinel lines. Whatever it prints, inspect the diff and untracked files yourself and run proportionate checks — a zero exit or a nonempty diff is not semantic completion, and `no-change` needs a convincing explanation in the report, not silence. On fix rounds, `ok` and `no-change` describe the round just run while `CHANGED_FILES` stays cumulative against the baseline. Any `POLICY_VIOLATION` that names drift ends the round: report the drift to the user and start nothing further until it is resolved. A moved `HEAD` or changed branch makes later runs re-derive their baseline from the drifted state, while staged work muddles attribution of the round's changes. `POLICY_VIOLATION=unknown` means the run failed before drift could be checked — see `ERROR`. Likewise when a failed run leaves a changed tree, surface the state to the user rather than repairing git state yourself.
4. Snapshot the round's diff into a temp directory, then convene a full hybrid review of the cumulative change against the baseline: Read `~/.claude/skills/hybrid-review/SKILL.md` and follow its procedure, running this skill's own `scripts/run-codex-council.sh` for the Codex adviser. Give the review packet the frozen specification and intent alongside the diff scope, and ask reviewers for approach-level recommendations, marked as such — accepting them is cheapest in round one. That document's read-only contract governs the review phase, which then hands its result to the next step rather than to the user — the loop resumes afterward.
5. Adjudicate every finding and approach-level recommendation yourself against the code — accepted major, accepted minor, or rejected, each with a reason — in a ledger file kept in a temp directory with stable finding IDs. The ledger travels in every later review and fix packet; a rejected finding reopens only on new evidence, never because another reviewer repeats it. Send only accepted findings to Codex as a self-contained fix packet: `${CLAUDE_SKILL_DIR}/scripts/run-codex-implement.sh resume <SESSION_ID> <fix-packet> /path/to/project` — resume preserves the implementer's context; start a fresh session instead when `SESSION_ID` is unknown or the fixes amount to a redesign. Verify the fix delta against each accepted finding and snapshot it; the per-round snapshots are what scope later delta reviews.
6. Review tiers and loop bounds: after a fix round, verify the delta yourself by default; convene another full hybrid review only when the round fixed accepted-major findings, the fix grew broad, architectural, or risky, or your own check surfaced a new major problem. At most five review rounds total, counting partial and failed ones so a broken council cannot loop forever. Hold a rising bar after round one: accept only regressions and clear correctness or security defects, not re-litigated decisions or scope creep — record improvement ideas for the final report instead. Stop early, end blocked, and escalate to the user when a rejected finding keeps returning or fix rounds introduce regressions twice. Before reporting `clean`, `minor-fixed`, or `capped`, run a terminal gate on the exact final tree: derive the cumulative change live at gate time from a fresh `git diff` against the recorded baseline commit plus the untracked files git currently reports; re-read that change against the frozen packet's acceptance criteria, constraints, and non-goals, and reconcile it against the full ledger; then run the project's relevant checks on the final tree yourself, treating Codex's `IMPLEMENT_TESTS` line only as a self-report. If the checks or anything else change project files, re-derive the cumulative change and repeat the gate — the re-read and the affected checks — once. If the tree still changes on that repeat, or a check produced a substantive, non-disposable change, record it as a gate finding and adjudicate it like any other; this does not authorize you to edit project files, and any needed fix still goes through Codex. Under a `HYBRID_IMPLEMENT_ALLOW_DIRTY=1` run, use the snapshots beside the first run's `PATCH_FILE` — `before.patch`, `before-status.txt`, and `before-untracked.txt` — to separate the user's pre-existing changes, and hold only the run's own work to the packet. These snapshots record pre-existing untracked files only as paths and hashes, so if the run's work touches one, attribution cannot be reconstructed; treat that overlap as uncertain and surface it to the user in the report rather than adjudicating it at the gate. Record anything the gate surfaces as a new ledger finding: send a minor defect to Codex for another fix round and rerun the gate afterward; for a major, broad, or risky defect, convene another full hybrid review as the review tiers above require. Across the whole run, allow at most two fix rounds caused directly or indirectly by gate findings, however they were routed, including through a gate-triggered full review. If the gate still fails after those rounds, or a required review no longer fits within the five-review-round cap, end capped rather than waiving verification. Any change to project files after the completed gate — beyond disposable artifacts already produced by the gate's checks — invalidates it and requires the entire gate to run again. For an ending that would be minor-fixed, you may additionally spot-check the final cumulative state with one read-only adviser (`council-fable` or `council-opus`), escalating to a full review if it finds a correctness or security defect. The spot-check does not consume one of the five review rounds, but a full review it triggers does; any fix round caused by a spot-check finding counts against the same two-round bound as gate-caused fixes.
7. Finish with an honest report: what was built and where, rounds run, findings accepted, rejected, and deferred with reasons, improvement ideas recorded rather than implemented, which checks ran and their results, the terminal gate's outcome or why it was not run, and the ending state — clean (the final cumulative state received a full review with no accepted findings, passed the terminal gate, and had no changes after that review beyond disposable artifacts produced by the gate's checks), minor-fixed (no changes beyond accepted-minor fixes and disposable artifacts produced by the gate's checks occurred after the last full review, the terminal gate passed, and the report discloses that those final deltas were lead-verified rather than council-reviewed), capped (only when the five-review-round cap or the two-round gate-fix bound prevented required work or convergence; list known unresolved findings separately from unperformed verification, including any fixes applied but never council-reviewed, and offer the user the option to authorize the additional review, fix, and gate work needed to continue), or blocked (policy drift from step 3; a rejected finding that keeps returning; fix rounds introducing regressions twice; the implementer safely stopped because the packet was ambiguous, internally inconsistent, infeasible, or materially unsafe; or an environment or tool condition prevented safe continuation; if the cumulative change is non-empty, explicitly state that the final tree was not verified by the terminal gate and describe what it contains). Never present the cap or a partial review as success.
