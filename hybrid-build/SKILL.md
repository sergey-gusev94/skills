# Hybrid Build

Act as the lead. This skill wraps `hybrid-implement`: pursue one frozen mandate through a living work queue, use investigation to discover and refine warranted work, and take each implementation increment through the full implement, review, fix, and terminal-gate procedure before committing it and starting the next. Stay in the main conversation — never run this skill or an increment inside a subagent.

For every increment, read `~/.claude/skills/imp/SKILL.md` and follow its full procedure, using this skill's own `scripts/run-codex-implement.sh` and `scripts/run-codex-council.sh` wherever that procedure invokes its scripts, including the council runner used for `hybrid-review`. Only Codex writes project files, and only through the implement script. You commit; Codex never does. Commit only under the protocol below. Never push, amend, rebase, run `git clean`, or otherwise rewrite or repair git state, and never set `HYBRID_IMPLEMENT_ALLOW_DIRTY=1`. Allow at most one active build run per repository and never two implement sessions at once. Invoking this skill is the user's standing authorization for autonomous planning, recorded scope-judgment decisions under the mandate's delegations, and one local commit per gated increment; it grants no authority beyond the mandate and this commit bound.

Never enter plan mode or seek plan or work queue approval; invoking this skill authorizes planning and proceeding autonomously within the mandate.

Within the mandate, choose and revise implementation approaches autonomously and record material decisions. This enclosing contract applies when preparing every `/imp` packet and overrides `/imp` step 1's raise-with-the-user instruction for approach choices within the mandate. Ask the user only when essential information cannot be established or proceeding needs authority the mandate does not grant; the integrity, history, and commit safeguards still apply.

Honor any ordering the mandate requests among discovery, investigation, and implementation; a requirement to investigate every candidate before making changes requires a full investigation pass before the first project modification. Adaptive selection never waives an explicit ordering. Absent instructions on continuing discovery, use the initial inventory within the recorded boundary as the stated assumption; record remaining or continuing discovery, revalidate changing eligibility facts when selecting work, and never silently claim coverage beyond that boundary.

## Durable state

**Disposable check artifacts** are outputs produced by checks that can be discarded without losing project work. They are neither persisted nor committed and do not fail cleanliness during post-gate, post-commit, or closing-gate work; this tolerance is transient, and anything whose disposability is unclear is surfaced instead of guessed. **Effective scope** is the frozen mandate plus user-authorized amendments. Resolve disposable check artifacts at frame time by using ignored paths or routing check outputs to ignored or external temporary locations. Mid-run, the lead may remove disposable artifacts positively attributable to its own check runs in this run and log their paths and attribution; surface anything else. This disposal permission does not authorize project-file edits.

Keep all run state in `$(git rev-parse --absolute-git-dir)/hybrid-build/`. This deterministic path is inside the git directory, invisible to `git status`, and survives compaction and reboots so a fresh session can resume without paths from conversation history:

- `scope.md` is the immutable mandate: the user's objective, required outcomes, constraints, exclusions, delegated decision rules, and completion conditions, preserved as either a verbatim copy of the source document or the normalized conversational scope. Never edit it; mid-run drift in the source document alone changes nothing, and user-authorized mandate amendments go in `progress.md` instead. Only a differing scope presented at re-invocation is a scope mismatch. Investigation results and work decomposition are derived run state: discovering, refining, or rejecting candidate work under delegated rules does not amend the mandate. Changing a binding requirement or constraint still requires user authorization unless that decision is delegated.
- `progress.md` must use `${CLAUDE_SKILL_DIR}/assets/progress-template.md` as its required format and stay current, including the scope source path and recorded hash produced by `sha256sum scope.md` in the state directory.
- `iterations/NNN/` contains that increment's frozen `/imp` packet, `/imp` step-7 final report, persisted gated change — the tracked patch and the path, mode, and content-hash identity of every untracked file in the gated tree, excluding disposable check artifacts — and resulting commit SHA.

When state exists, re-read `scope.md`, `progress.md`, and `git log` on invocation and before every iteration; never rely on conversation memory. Existing state without a coherent frame — including no valid run state in `progress.md` — is an incomplete frame: surface it and reframe with the user. Otherwise first compare the recorded hash in `progress.md` against a fresh `sha256sum scope.md` in the state directory. Only after integrity passes, compare the scope now presented — the source document's current content or the normalized conversational scope — with the frozen copy; a re-invocation that presents no scope matches by definition.

On invocation, evaluate these cases in order:

1. **No state directory:** go directly to Frame the run.
2. **Failed integrity check:** mark the run `blocked` and halt for the user.
3. **Scope matches `running`:** resume from the work queue.
4. **Scope matches `done`:** the run is already complete.
5. **Scope matches `capped` or `blocked`:** resume only after the user resolves the cause and asks to continue, then mark it `running`.
6. **Scope mismatches `running`:** leave the live run and its recorded state unchanged, refuse this invocation, and ask the user.
7. **Scope mismatches terminal `done`, `capped`, or `blocked`:** under the archive rule below, archive the old state files in a timestamped subdirectory within `hybrid-build/`, then frame a new run.

At the user's explicit direction, likewise archive and frame afresh when abandoning a mismatched `running` run, keeping an intentional history rewrite, or discarding unusable state. Before archiving any run not ended `done`, surface unresolved blockers such as an unverified loop commit or dirty tree and obtain the user's disposition; never let a blocker silently become the new run's baseline.

### Interrupted-increment reconciliation

Run these cases in order for iteration and closing preflight; this procedure completes preflight without calling iteration step 1. Reclaim any item left `in-progress` as the interrupted or halted increment.

1. **Branch or ancestry mismatch:** require the branch recorded in `progress.md`. If it changed, or `HEAD` moved from the recorded current-baseline commit and `git merge-base --is-ancestor <current-baseline> HEAD` fails, mark the run `blocked`, halt, and obtain the user's decision. Never adopt or repair a reset, rebase, amend, or other non-descendant history change. At the user's direction, archive an intentionally rewritten run under the archive rule and frame afresh; never adopt the rewrite into the current run.
2. **Dirty tree:** require a clean tree apart from disposable check artifacts. If the dirty tree, apart from disposable check artifacts, exactly matches the interrupted increment's persisted gated change, continue with its commit protocol instead of halting. Surface any other dirty tree, mark the run `blocked`, and halt for the user.
3. **Clean descendant `HEAD` with an interrupted increment:** inspect the commits before adopting them. A commit belongs to the interrupted increment when its subject names the work queue item's stable ID or its iteration directory records that SHA. Compare it with the persisted gated change; if they match, finish the interrupted bookkeeping — record the SHA, mark the item `done@<commit>`, and advance the current baseline — instead of rerunning it. If they differ or the comparison cannot be established, mark the run `blocked` and treat the commit as unverified loop work under the commit protocol. If the user chooses to keep it, mark the run `running`, record the SHA, mark the item `done@<commit>` with an unverified-loop-work note, advance the current baseline, and require the cumulative closing review; never classify that commit as out of scope.
4. **Remaining descendant commits:** record a user commit that resolves a logged closing-gate finding as gate-finding work included in cumulative review scope; adopt only the rest as non-loop work, logging their range and marking only that range out of scope. Advance the current baseline to `HEAD`.
5. **Unfinished interrupted item without a reconciled loop commit:** reclaim the item and continue at iteration step 2, where steps 2–4 perform revalidation, a fresh packet freeze under `iterations/NNN/`, and a fresh Codex session. Preflight itself never freezes packets or launches sessions.

## Frame the run

1. Preflight first: require a git repository with at least one commit, an empty `git status --porcelain`, and no merge, rebase, or cherry-pick in progress. Arrange disposable check outputs at frame time as above; have the user resolve existing non-ignored artifacts by removing them at their direction or gitignoring them, since the implement script requires a strictly clean tree. An untracked scope document inside the project also blocks the run, so have the user commit it or keep it outside the tree. Work on the checked-out branch. If concurrent third-party work dirties a shared checkout and blocks preflight, propose a linked worktree, subject to the mandate's branch constraints; its run state resolves via `git rev-parse --absolute-git-dir` to `.git/worktrees/<name>/hybrid-build/`.
2. Freeze the mandate in `scope.md` and run `sha256sum scope.md` in the state directory to obtain its integrity hash. Seed the work queue with obligations identifiable without investigation; exhaustiveness is not required, and a single discovery item such as `enumerate the work the mandate defines` is a valid seed. Record in `progress.md` whether obligations are listed directly or defined by a rule whose instances investigation must find, the enumeration procedure, and the discovery boundary: sources, observed candidate set (or not yet observed), and observation time or equivalent. Complete the initial inventory record as discovery proceeds. Use stable, never-reused item IDs; retire items by state, never delete or renumber them. Implementation increments must be independently implementable and reviewable and leave the repository working with relevant checks passing. Coherence, not a numeric size cap, sets their boundary; an increment too small wastes a full implement-and-review cycle.
3. With preflight still satisfied, write `progress.md` with `running`, the checked-out branch, the initial work queue and discovery record, the scope source path (or conversational origin) and recorded hash, and the same commit as both loop baseline and current baseline. State the initial work queue to the user in a few lines as you begin and proceed without waiting for a reply. This completes the frame; only then start the first iteration.

## Implement each increment

1. Re-read durable state and run Interrupted-increment reconciliation in full for branch, ancestry, clean-tree checks, the exact persisted-gate exception, and classification and adoption of descendant commits. Do not select pending work until preflight and any interrupted bookkeeping have completed; an unfinished interrupted item returns to step 2 for revalidation.
2. Perform the primary planning act: before selecting work, including on resumption under invocation case 5, return any item whose recorded blocking cause is resolved to `pending` and log the resolution as evidence. Investigate read-only and revalidate the reclaimed item or select the next pending item against the current code, the mandate, dependencies, requested ordering, and current eligibility. When an item cannot proceed because it awaits a user decision, an external prerequisite, or a dependency outside the run's authority, and independent work remains, park it as `blocked: <cause>` and record the cause. Add items when evidence shows the work queue is missing work traceable to the mandate; split, merge, or reorder items as needed. Log every addition, split, merge, reorder, and retirement with its evidence, preserving IDs and recording successor IDs for split or merged items. Use `merged-into: <ID>` for a merged item; its obligations remain with its successor. Read-only investigation and work queue decisions cost no `/imp` cycle. For discovery and investigation items whose deliverable is knowledge, an inventory, or dispositions, record `completed-by-investigation: <evidence>` when the lead's read-only work completes that deliverable; these items need no `/imp` run. An implementation obligation retires only through a commit, `/imp`-backed `satisfied-by-prior-work: <evidence>`, or the drop rule. The lead's read-only conclusion that an implementation obligation is already satisfied selects a `/imp` run to confirm no-change, never a lead-only retirement. Apply this two-tier drop rule:
   - **Judgment skip:** autonomously reject a candidate as unwarranted — not a real defect, already satisfied, superseded, or outside the mandate's intent — only under a decision rule the mandate delegates. Record `skipped: <evidence>` with the supporting evidence and delegated rule, and include it in the final report; the mandate's delegation is the confirmation.
   - **Dropping a user-stated obligation:** abandoning an outcome the user explicitly required changes the mandate and requires recorded justification and user confirmation, unless that judgment was itself delegated. Record `dropped: <reason>` and the required authorization; delegated candidate rejections use `skipped` instead.
   - In either tier, never drop (or skip) merely because it is hard; unresolved warranted work stays pending or blocked and is never relabeled unwarranted.

   Put work that cannot be traced to the effective scope on the deferred list and report it at the end; do not implement it. After a discovery pass or a drop or skip, record its dispositions and continue planning; run steps 3–4 only for an item that remains selected for implementation.
3. Write a self-contained `/imp` packet for this item alone: objective, acceptance criteria, constraints, non-goals, pointers to relevant files, checks to run, and the rejected-findings digest as prior rejections. Bound the packet to this increment's acceptance criteria, prohibit unrelated changes and advancing other work queue items, name adjacent known items only where needed to prevent confusion, and require Codex to report newly discovered work to the lead instead of doing it. Freeze it under `iterations/NNN/` and mark the item `in-progress`.
4. Before launching the fresh implement run for an increment, require an empty `git status --porcelain`; remove and log only disposable artifacts positively attributable to this run's own checks under the Durable state section's disposal permission, and surface anything else that prevents strict cleanliness. Then follow `/imp` through its terminal gate with a fresh Codex session for the increment; `resume` is only `/imp`'s within-increment fix mechanism. Save its step-7 report under `iterations/NNN/`. If it ends `blocked` because the implementer identified a defect in the lead's own packet, and the runner reports zero changed files with a clean tree and no policy drift, correct the packet within the mandate, re-freeze it under a fresh `iterations/NNN/`, and retry with a fresh session. Allow at most two such retries per item across the run, logging each defect, correction, and attempt; this is the sole exception to the blocked-run halt below. If correction needs missing information or authority, or another retry would exceed this bound, mark the run `blocked` and halt. Otherwise act on the ending state under the commit protocol, update `progress.md`, and put only a two-to-three-line summary in the conversation: the item, ending state and commit or evidence-bearing decision, and work remaining. Then continue from durable state.

## Commit protocol

Commit only between iterations and never while an implement or council script run is outstanding. On `clean` or `minor-fixed`, first persist the exact gated change under `iterations/NNN/`, excluding disposable check artifacts, then stage and commit exactly that change and no artifacts using a repository-style message whose subject names the work queue item's stable ID. If a hook blocks the commit, disclose that fact, rerun the gate and refresh the persisted gated change before retrying, and never bypass it with `--no-verify`. After a commit succeeds, verify that the tree is clean apart from disposable check artifacts and the committed content matches the persisted gated change. If the created commit differs, including when a hook rewrote files but let the commit succeed, mark the run `blocked`, disclose that the commit is unverified, and halt; never amend it or add a corrective commit for that increment. If the user later keeps that commit, finish its bookkeeping under Interrupted-increment reconciliation and retain it as loop work requiring cumulative closing review, not adopted out-of-scope work. Surface unattributed leftover files instead of sweeping them into the commit. Otherwise record the commit SHA under `iterations/NNN/` and in `progress.md`, mark the item `done@<commit>`, and advance the current baseline to that SHA.

A completed `/imp` run whose convincing no-change result shows the item was already satisfied is a successful outcome: mark it `satisfied-by-prior-work: <evidence>` and create no empty commit. On `capped` or `blocked`, except for the bounded packet retry in iteration step 4, update the run state and halt the entire loop without committing. A capped increment has unresolved findings or unperformed verification, and later work must not build on it. Report the ending state and uncommitted tree to the user; after resolution, re-invocation resumes from deterministic state.

## Close the run

There is no numeric iteration cap. An iteration qualifies when it produces a commit, `/imp`-backed `satisfied-by-prior-work: <evidence>`, `completed-by-investigation: <evidence>`, a drop or skip logged under the drop rule, a recorded evidence-bearing work queue decision, or recorded new discovery evidence in the discovery record. Reset the stagnation counter on a qualifying iteration; increment it on each consecutive non-qualifying iteration, and mark the run `blocked` and halt for the user on the second. An attempt handled under iteration step 4's bounded packet-retry rule neither qualifies nor updates the stagnation counter; the two-retry-per-item bound governs it. A `/imp` run reporting no-change without a convincing already-satisfied explanation still blocks. A `capped` or `blocked` iteration's own halt cause takes precedence over both the qualification rule and the stagnation rule; iteration step 4's bounded packet retry is the sole exception to that halt-cause precedence. Before continuing, record the iteration's outcome and updated stagnation counter in `progress.md`, including for read-only iterations.

Unresolved `blocked: <cause>` items halt the run without a closing gate. When no pending, in-progress, or blocked work remains, run this closing gate; an empty work queue triggers the gate and never substitutes for it.

1. **Preflight and reconciliation:** run the iteration preflight in full, including Interrupted-increment reconciliation and classification, adoption, and logging of descendant commits. If preflight restores an item to the loop, continue the loop. A commit the user made to resolve a prior closing-gate finding remains gate-finding work included in cumulative review scope, never adopted out of scope.
2. **Gate start conditions:** begin on the exact final tree, require it to be clean apart from disposable check artifacts, and record the starting branch and `HEAD`.
3. **Re-derive warranted work:** re-run the recorded enumeration procedure within the recorded discovery boundary against the final state. Every candidate must carry a supported disposition under the mandate. Verify every required outcome and accepted item under the effective scope against the final tree; a commit reference is provenance, not proof the requirement still holds. `/imp`-backed `satisfied-by-prior-work: <evidence>` and `completed-by-investigation: <evidence>` are valid dispositions for implementation obligations and discovery or investigation items respectively. Exclusions must follow the recorded decision rules or a user authorization. Record anything untraced as a closing-gate finding routed through step 6's adjudication.
4. **Project checks:** run the project's relevant checks. A substantive, non-disposable project-file change produced by a check marks the run `blocked`: record it as a closing-gate finding, surface the dirty tree to the user and never commit the ungated content; after the user resolves it, re-invocation resumes from the work queue, and the closing gate runs again when its entry condition holds.
5. **Cumulative review:** for a multi-increment run or any run retaining unverified loop work or gate-finding work, also read `~/.claude/skills/hybrid-review/SKILL.md` and follow its full procedure, using this skill's council script, to review the cumulative loop-baseline-to-`HEAD` change against the effective scope. Give the review packet the mandate, amendments, discovery record, candidate dispositions, and final-state evidence; explicitly ask whether any obligation is untraced. Identify every adopted non-loop commit range as out of scope and include retained unverified loop commits and gate-finding work as work requiring verification. Disclose and use a completed review labeled partial. Only when no closing review can be produced at all may you retry once; if the retry also produces no review, mark the run `capped` and halt.
6. **Adjudication and rising bar:** record every closing-gate finding — a failing project check, untraced effective-scope element, substantive check-produced change, or other defect — and adjudicate it like a review finding. Accepted findings become work queue items and the loop continues; a finding that cannot be addressed through an increment or needs the user's decision halts with the state its cause dictates. Adjudicate findings from every completed review as usual, but on second and later closing-review rounds accept only regressions and clear correctness or security defects and record other findings for the final report. The rising bar never waives required outcomes, acceptance criteria, discovery coverage, or mandatory verification. Record each closing round and outcome in `progress.md`.
7. **End-of-gate stability:** at gate completion, including after the cumulative review, confirm that the branch, `HEAD`, and tree apart from disposable check artifacts are unchanged since the gate began; if any changed, the gate is invalid and must restart from full preflight.

Finish with an honest report and exactly one current state, recorded in `progress.md`: `done` when every required outcome under the effective scope is verified, every candidate within the recorded boundary has a supported disposition, and the last closing gate passed; `capped` when the run is currently halted because an increment's `/imp` run ended capped or required closing verification could not be completed; or `blocked` when the run is currently halted by an unresolved blocked increment, policy drift, two consecutive non-qualifying iterations, unverified commit, dirty gate finding, failed state-integrity check, or decision only the user can make. A resolved halt does not carry forward after the run resumes, so a run whose last state passed the closing gate ends `done`. Never present a halt as success. List every item with its commit or supported disposition and ending state, amendments and drops with reasons and required authorization, judgment skips with evidence, discovery coverage and remaining blockers, deferred out-of-scope ideas, checks run, and the state directory path.

Archive, do not author: the frozen increment packet, `/imp` report, and commit message describe each change; generate no separate per-commit document. When an increment changes behavior described by the project's own documentation, that documentation update is part of the coherent increment and belongs in the same commit.
